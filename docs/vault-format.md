# Vault format specification

| | |
| --- | --- |
| **Status** | Draft skeleton. Not stable. |
| **Format version** | 0 (pre-release) |
| **Applies to** | NovaVault pre-1.0 development builds |

> [!WARNING]
> This is a skeleton of the public specification. Structure and intent are described here, but field sizes, encodings, identifiers and parameter values are **to be finalized in the core implementation** (`crates/novavault-core`). The format may change incompatibly until version 1.0. Do not rely on it for real data.

## 1. Scope and goals

This document specifies the on-disk format of a NovaVault vault so that it can be reviewed independently and, in principle, read by an independent implementation.

Design goals:

- **Confidentiality and integrity** of all user data using audited primitives only.
- **Two key slots** (master password and recovery code) that each unlock the same vault key.
- **Cheap secret rotation:** changing the master password or regenerating the recovery code rewrites only one key slot.
- **Versioned and self-describing:** a reader can tell which version and which algorithms a file uses before attempting to decrypt it.
- **Strict parsing:** any unknown, malformed or unauthenticated input is rejected.

## 2. Conventions

- The key words MUST, MUST NOT, SHOULD and MAY are used as described in RFC 2119.
- Multi-byte integers are unsigned and little-endian unless stated otherwise. *(To be finalized in the core implementation.)*
- `||` denotes byte concatenation. `len(x)` is the length of `x` in bytes.
- All random values are generated with the operating system CSPRNG.
- Field sizes marked *TBF* are to be finalized in the core implementation.

## 3. Cryptographic primitives

| Purpose | Algorithm | Notes |
| ------- | --------- | ----- |
| Key derivation | Argon2id (RFC 9106) | Parameters stored per key slot. Minimum values enforced by readers: *TBF*. |
| Authenticated encryption | XChaCha20-Poly1305 **or** AES-256-GCM | The choice for format version 1 is *to be finalized in the core implementation*. The header records the algorithm identifier so the decision is explicit in every file. |
| Vault key | 256-bit random key | Generated once at vault creation. |
| Randomness | OS CSPRNG | Used for the vault key, salts, nonces and the recovery code. |

No custom primitives are used. Crate choices and their justification will be documented separately in `docs/`.

## 4. File layout overview

A vault is a single file consisting of the following sections, in order:

```text
+----------------------+
| Header               |  plaintext, authenticated
+----------------------+
| Key slot table       |  password slot, recovery slot
+----------------------+
| Record section       |  encrypted records
+----------------------+
| Attachment section   |  encrypted, chunked attachment data
+----------------------+
```

Whether records and attachments live in a single file, in an append-only log, or in a container (for example a SQLite database with encrypted values) is *to be finalized in the core implementation*. The logical structure described below applies regardless of container.

Writes MUST be atomic: a new version of the file is written to a temporary file in the same directory, flushed, and then renamed over the old one.

## 5. Header

The header identifies the file and its parameters. It is stored in plaintext so a reader can select the right algorithms, and it is authenticated by being included as associated data (see §6.3 and §7.2).

| Field | Size | Description |
| ----- | ---- | ----------- |
| `magic` | *TBF* | Fixed byte string identifying a NovaVault file. |
| `format_version` | *TBF* | Format version number. This document describes version 0. |
| `aead_id` | *TBF* | Identifier of the AEAD algorithm used for all ciphertexts in the file. |
| `vault_id` | 16 bytes *(TBF)* | Random identifier, bound into associated data so ciphertexts cannot be moved between vaults. |
| `flags` | *TBF* | Reserved. MUST be zero in version 0; readers MUST reject unknown flags. |
| `slot_count` | *TBF* | Number of key slots that follow. |

*Exact field order, sizes and the `magic` value are to be finalized in the core implementation.*

## 6. Key slots

### 6.1 Purpose

The vault key is never stored in the clear. It is stored wrapped (encrypted) once per key slot. Version 0 defines exactly two slot types:

| Slot type | Secret | Required |
| --------- | ------ | -------- |
| `password` | Master password chosen by the user | Exactly one |
| `recovery` | Emergency recovery code generated by NovaVault | Exactly one |

Either slot alone is sufficient to recover the vault key.

### 6.2 Slot structure

| Field | Size | Description |
| ----- | ---- | ----------- |
| `slot_type` | *TBF* | `password` or `recovery`. |
| `kdf_salt` | 16 to 32 bytes *(TBF)* | Random per-slot salt. A new salt MUST be generated whenever the slot is rewritten. |
| `kdf_memory_kib` | *TBF* | Argon2id memory cost. |
| `kdf_iterations` | *TBF* | Argon2id time cost. |
| `kdf_parallelism` | *TBF* | Argon2id lanes. |
| `nonce` | AEAD nonce size | Random nonce for wrapping. |
| `wrapped_key` | 32 bytes + tag | Vault key encrypted under the slot's wrapping key. |

### 6.3 Wrapping and unwrapping

```text
wrapping_key = Argon2id(secret, kdf_salt, memory, iterations, parallelism, out_len = 32)
wrapped_key  = AEAD_Encrypt(wrapping_key, nonce, vault_key, ad = header || slot_metadata)
```

`slot_metadata` is every slot field except `nonce` and `wrapped_key`. Unwrapping performs the same derivation and `AEAD_Decrypt`; an authentication failure MUST be reported as a single generic error that does not distinguish a wrong secret from a corrupted slot.

Normalization of the master password (for example Unicode NFC) before derivation is *to be finalized in the core implementation*.

### 6.4 Rotation

- **Changing the master password** derives a new wrapping key with a fresh salt and nonce and replaces the `password` slot. The vault key, records and attachments are unchanged.
- **Regenerating the recovery code** does the same for the `recovery` slot. The previous recovery code no longer opens the vault once the new file is written.
- KDF parameters MAY be increased during either operation.

## 7. Encrypted records

### 7.1 Record types

Version 0 defines three record types: `password`, `note` and `secret`. The field schema of each type (for example title, username, URL, notes, custom fields) is *to be finalized in the core implementation*.

### 7.2 Record envelope

Each record is stored as an envelope:

| Field | Size | Description |
| ----- | ---- | ----------- |
| `record_id` | 16 bytes *(TBF)* | Random, unique within the vault. |
| `record_type` | *TBF* | One of the record types above. |
| `nonce` | AEAD nonce size | Fresh random nonce for every write of the record. |
| `ciphertext` | variable | AEAD encryption of the serialized record payload, including the tag. |

```text
ad         = vault_id || format_version || record_id || record_type
ciphertext = AEAD_Encrypt(record_key, nonce, payload, ad)
```

Whether `record_key` is the vault key directly or a per-purpose subkey derived from it (for example with HKDF) is *to be finalized in the core implementation*. The payload serialization format and whether payloads are padded to hide their length are also *to be finalized in the core implementation*.

Timestamps and other metadata that are not needed before decryption SHOULD be stored inside the encrypted payload.

## 8. Attachments

- An attachment belongs to exactly one record. The owning record's encrypted payload stores the attachment's identifier, file name, media type and size, so none of these are visible in plaintext.
- Attachment data is split into fixed-size chunks (size *TBF*) and each chunk is encrypted separately so large files can be streamed without loading them fully into memory.
- Each chunk's associated data MUST bind `vault_id`, the attachment identifier, the chunk index and a final-chunk marker, so chunks cannot be reordered, dropped, duplicated or truncated undetected.
- The exact chunking scheme (for example a STREAM construction) is *to be finalized in the core implementation*.

## 9. Recovery code

- Generated from the OS CSPRNG with at least 128 bits of entropy *(exact length TBF)*.
- Presented in a human-readable form: groups of characters from an unambiguous alphabet (excluding look-alikes such as `0`/`O` and `1`/`l`), separated by dashes, with a checksum to catch typos. *Alphabet, grouping and checksum are to be finalized in the core implementation.*
- Shown once at creation and at each regeneration. The user MUST confirm they saved it before the operation completes.
- Before derivation, input is normalized (case and separators removed) so formatting differences do not matter.

## 10. Versioning and compatibility

- Every file carries `format_version`. Readers MUST reject versions they do not support and MUST NOT attempt best-effort parsing.
- Any change to the on-disk format requires a version bump, an update to this specification and a migration path that upgrades older vaults on unlock.
- Migrations rewrite the file atomically and SHOULD keep a backup of the previous file until the new one has been verified.
- Format version 1 will be the first stable version and will be declared at the NovaVault 1.0 release.

## 11. Validation rules for readers

A conforming reader MUST:

1. Check `magic` and `format_version` before parsing anything else.
2. Reject unknown `aead_id`, slot types, record types and non-zero reserved flags.
3. Enforce minimum Argon2id parameters and upper bounds on all lengths before allocating memory.
4. Treat any authentication failure as fatal for the affected item and never return unauthenticated plaintext.

## 12. Test vectors

Known-answer test vectors for key derivation, slot unwrapping, record decryption and attachment chunks will be published here and in the core crate's tests once the format is finalized.
