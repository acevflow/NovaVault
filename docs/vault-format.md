# Vault format specification

| | |
| --- | --- |
| **Status** | Draft. Key slots and recovery code specified; other sections are a skeleton. Not stable. |
| **Format version** | 0 (pre-release) |
| **Applies to** | NovaVault pre-1.0 development builds |

> [!WARNING]
> This is a draft of the public specification. Key slots (§6) and the recovery code (§9) are specified; for the other sections, structure and intent are described here, but field sizes, encodings, identifiers and parameter values are **to be finalized in the core implementation** (`crates/novavault-core`). The format may change incompatibly until version 1.0. Do not rely on it for real data.

## 1. Scope and goals

This document specifies the on-disk format of a NovaVault vault so that it can be reviewed independently and, in principle, read by an independent implementation.

Design goals:

- **Confidentiality and integrity** of all user data using audited primitives only.
- **Two key slots** (master password and recovery code) that each unlock the same vault key.
- **Cheap secret rotation:** changing the master password or regenerating the recovery code rewrites only one key slot.
- **Versioned and self-describing:** a reader can tell which version and which algorithms a file uses before attempting to decrypt it.
- **Strict parsing:** any unknown, malformed or unauthenticated input is rejected.

## 2. Conventions

- The key words MUST, MUST NOT, SHOULD and MAY are used as described in RFC 2119.
- Multi-byte integers are unsigned and little-endian unless stated otherwise. *(To be finalized in the core implementation.)*
- `||` denotes byte concatenation. `len(x)` is the length of `x` in bytes.
- All random values are generated with the operating system CSPRNG.
- Field sizes marked *TBF* are to be finalized in the core implementation.

## 3. Cryptographic primitives

| Purpose | Algorithm | Notes |
| ------- | --------- | ----- |
| Key derivation | Argon2id v0x13 (RFC 9106) | Parameters stored per key slot. Readers MUST reject memory below 19 MiB or above 4 GiB, iterations below 2 or above 64, and parallelism below 1 or above 16. Writers use 64 MiB, 3 iterations and 4 lanes by default. Output is 32 bytes. |
| Authenticated encryption | XChaCha20-Poly1305 (draft-irtf-cfrg-xchacha) | 256-bit key, 24-byte random nonce, 16-byte tag. Rationale in [architecture.md](architecture.md#why-xchacha20-poly1305-rather-than-aes-gcm). The header records the algorithm identifier so the choice is explicit in every file. |
| Vault key | 256-bit random key | Generated once at vault creation. |
| Randomness | OS CSPRNG | Used for the vault key, salts, nonces and the recovery code. |

No custom primitives are used. Crate choices and their justification are documented in [architecture.md](architecture.md#dependencies).

## 4. File layout overview

A vault is a single file consisting of the following sections, in order:

```text
+----------------------+
| Header               |  plaintext, authenticated
+----------------------+
| Key slot table       |  password slot, recovery slot
+----------------------+
| Record section       |  encrypted records
+----------------------+
| Attachment section   |  encrypted, chunked attachment data
+----------------------+
```

Whether records and attachments live in a single file, in an append-only log, or in a container (for example a SQLite database with encrypted values) is *to be finalized in the core implementation*. The logical structure described below applies regardless of container.

Writes MUST be atomic: a new version of the file is written to a temporary file in the same directory, flushed, and then renamed over the old one.

## 5. Header

The header identifies the file and its parameters. It is stored in plaintext so a reader can select the right algorithms, and it is authenticated by being included as associated data (see §6.3 and §7.2).

| Field | Size | Description |
| ----- | ---- | ----------- |
| `magic` | *TBF* | Fixed byte string identifying a NovaVault file. |
| `format_version` | *TBF* | Format version number. This document describes version 0. |
| `aead_id` | *TBF* | Identifier of the AEAD algorithm used for all ciphertexts in the file. |
| `vault_id` | 16 bytes *(TBF)* | Random identifier, bound into associated data so ciphertexts cannot be moved between vaults. |
| `flags` | *TBF* | Reserved. MUST be zero in version 0; readers MUST reject unknown flags. |
| `slot_count` | *TBF* | Number of key slots that follow. |

*Exact field order, sizes and the `magic` value are to be finalized in the core implementation.*

## 6. Key slots

### 6.1 Purpose

The vault key is never stored in the clear. It is stored wrapped (encrypted) once per key slot. Version 0 defines exactly two slot types:

| Slot type | Secret | Required |
| --------- | ------ | -------- |
| `password` | Master password chosen by the user | Exactly one |
| `recovery` | Emergency recovery code generated by NovaVault | Exactly one |

Either slot alone is sufficient to recover the vault key.

### 6.2 Slot structure

A key slot is exactly 101 bytes. Integers are unsigned little-endian.

| Offset | Field | Size | Description |
| ------ | ----- | ---- | ----------- |
| 0 | `slot_type` | 1 byte | `0x01` = `password`, `0x02` = `recovery`. Readers MUST reject any other value. |
| 1 | `kdf_salt` | 16 bytes | Random per-slot salt. A new salt MUST be generated whenever the slot is rewritten. |
| 17 | `kdf_memory_kib` | 4 bytes (u32) | Argon2id memory cost in KiB. |
| 21 | `kdf_iterations` | 4 bytes (u32) | Argon2id time cost. |
| 25 | `kdf_parallelism` | 4 bytes (u32) | Argon2id lanes. |
| 29 | `nonce` | 24 bytes | Random XChaCha20-Poly1305 nonce for wrapping. |
| 53 | `wrapped_key` | 48 bytes (32 + 16-byte tag) | Vault key encrypted under the slot's wrapping key, followed by the Poly1305 tag. |

`slot_metadata` is bytes 0–28 (`slot_type` to `kdf_parallelism`, 29 bytes). Readers MUST reject a slot whose length is not exactly 101 bytes or whose KDF parameters are outside the bounds in §3, before running Argon2id.

The key slot table holds exactly one `password` slot followed by one `recovery` slot. How the table is framed inside the file (and how `slot_count` in the header relates to it) is *to be finalized with the header*.

### 6.3 Wrapping and unwrapping

```text
wrapping_key = Argon2id(secret, kdf_salt, memory, iterations, parallelism, out_len = 32)
nonce        = random(24)
wrapped_key  = XChaCha20-Poly1305_Encrypt(wrapping_key, nonce, vault_key, ad = header || slot_metadata)
```

`header` is the authenticated encoding of the vault header (§5). Because `slot_metadata` has a fixed length, the concatenation is unambiguous. Binding both into the associated data means changing a slot's type, salt or KDF parameters, or moving a slot to another vault, makes unwrapping fail.

Unwrapping performs the same derivation and `XChaCha20-Poly1305_Decrypt`. An authentication failure MUST be reported as a single generic error that does not distinguish a wrong secret, a wrong header or a corrupted slot.

The `secret` input is:

- **`password` slot:** the UTF-8 bytes of the master password, exactly as entered. Unicode normalization (for example NFC) is *to be finalized before format version 1*; until then, a password typed with a different Unicode composition will not match.
- **`recovery` slot:** the 32 ASCII bytes of the recovery code in canonical form (§9): upper case, no separators, checksum symbols included.

### 6.4 Operations

- **Create:** generate a random 256-bit vault key and a new recovery code, then write a `password` slot and a `recovery` slot that both wrap the vault key.
- **Unlock:** unwrap the `password` slot with the master password, or the `recovery` slot with the recovery code. Both yield the same vault key.
- **Change the master password:** with the vault key from any unlock (including one with the recovery code, for a forgotten password), write a new `password` slot with a fresh salt and nonce. The vault key, the `recovery` slot, records and attachments are unchanged.
- **Regenerate the recovery code:** generate a new code and write a new `recovery` slot with a fresh salt and nonce. The previous code no longer opens the vault once the new file is written. The `password` slot is unchanged.
- KDF parameters MAY be increased during either rotation.
- A new slot is fully computed before it replaces the old one, and the file is written atomically (§4), so a failed rotation leaves the vault openable with the previous secrets.

## 7. Encrypted records

### 7.1 Record types

Version 0 defines three record types: `password`, `note` and `secret`. The field schema of each type (for example title, username, URL, notes, custom fields) is *to be finalized in the core implementation*.

### 7.2 Record envelope

Each record is stored as an envelope:

| Field | Size | Description |
| ----- | ---- | ----------- |
| `record_id` | 16 bytes *(TBF)* | Random, unique within the vault. |
| `record_type` | *TBF* | One of the record types above. |
| `nonce` | 24 bytes | Fresh random nonce for every write of the record. |
| `ciphertext` | variable | AEAD encryption of the serialized record payload, including the tag. |

```text
ad         = vault_id || format_version || record_id || record_type
ciphertext = AEAD_Encrypt(record_key, nonce, payload, ad)
```

Whether `record_key` is the vault key directly or a per-purpose subkey derived from it (for example with HKDF) is *to be finalized in the core implementation*. The payload serialization format and whether payloads are padded to hide their length are also *to be finalized in the core implementation*.

Timestamps and other metadata that are not needed before decryption SHOULD be stored inside the encrypted payload.

## 8. Attachments

- An attachment belongs to exactly one record. The owning record's encrypted payload stores the attachment's identifier, file name, media type and size, so none of these are visible in plaintext.
- Attachment data is split into fixed-size chunks (size *TBF*) and each chunk is encrypted separately so large files can be streamed without loading them fully into memory.
- Each chunk's associated data MUST bind `vault_id`, the attachment identifier, the chunk index and a final-chunk marker, so chunks cannot be reordered, dropped, duplicated or truncated undetected.
- The exact chunking scheme (for example a STREAM construction) is *to be finalized in the core implementation*.

## 9. Recovery code

- **Alphabet:** the 32 symbols `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`, where symbol `i` has value `i`. The look-alikes `0`, `1`, `O` and `I` are excluded.
- **Random part:** 30 symbols. Each symbol is the low 5 bits of a byte from the OS CSPRNG; since 256 is a multiple of 32 this is uniform, giving 150 bits of entropy.
- **Checksum:** with `v[0..30]` the values of the random symbols, `c = (Σ (i + 1) · v[i]) mod 1021`, appended as two symbols with values `c / 32` and `c mod 32`. Because 1021 is a prime larger than every weight and every symbol difference, the checksum detects every single-symbol substitution and every swap of two adjacent symbols in the random part, and every single-symbol substitution in the checksum. It is a typo check, not a security mechanism.
- **Canonical form:** the 32 symbols (random part then checksum), upper case, no separators. This is the Argon2id input (§6.3).
- **Display form:** the canonical form in 8 groups of 4 symbols separated by `-`, for example `ABCD-EFGH-JKLM-NPQR-STUV-WXYZ-2345-6789`.
- **Parsing:** input is upper-cased and `-` and whitespace are removed. Readers MUST then reject input that does not have exactly 32 symbols, contains a character outside the alphabet, or fails the checksum, before running Argon2id.
- Shown once at creation and at each regeneration. The user MUST confirm they saved it before the operation completes (an application-level step). The vault never stores the code itself.

Test vector: a random part of 30 × `3` (value 1) has checksum `465 = 14 · 32 + 17`, so the code is `3333-3333-3333-3333-3333-3333-3333-33GK`.

## 10. Versioning and compatibility

- Every file carries `format_version`. Readers MUST reject versions they do not support and MUST NOT attempt best-effort parsing.
- Any change to the on-disk format requires a version bump, an update to this specification and a migration path that upgrades older vaults on unlock.
- Migrations rewrite the file atomically and SHOULD keep a backup of the previous file until the new one has been verified.
- Format version 1 will be the first stable version and will be declared at the NovaVault 1.0 release.

## 11. Validation rules for readers

A conforming reader MUST:

1. Check `magic` and `format_version` before parsing anything else.
2. Reject unknown `aead_id`, slot types, record types and non-zero reserved flags.
3. Enforce minimum Argon2id parameters and upper bounds on all lengths before allocating memory.
4. Treat any authentication failure as fatal for the affected item and never return unauthenticated plaintext.

## 12. Test vectors

Known-answer test vectors for key derivation, slot unwrapping, record decryption and attachment chunks will be published here and in the core crate's tests once the format is finalized.
